# セキュリティ設計と監査対応（対策案）

本書では、Home Status におけるアーキテクチャ上のセキュリティ監査項目と、今後の改善に向けた対策案を記録します。

---

## 1. ルーター管理画面の同一オリジンプロキシ

### 現状とリスク
- **現状**: ローカルルーターの Web 管理画面をステータスボードと同一オリジン上で中継（プロキシ）する構成。
- **リスク**: ルーターの Web 画面が同一オリジン上で配信される場合、ルーター側のファームウェアに脆弱性や未検証スクリプトが存在すると、同一オリジンで動作するステータスボードの DOM、LocalStorage、Cookie、API に影響が波及する恐れがあります。

### 対策案
1. **別サブドメインへの分離（推奨）**
   - ルーター管理用の中継を独立したサブドメイン（例: `router.example.com`）に分離し、個別のアクセス制御ポリシーを適用する。
   - これにより、メインのステータスボードのオリジンと実行コンテキスト・ストレージを完全に分離する。
2. **サンドボックス化 iframe の活用**
   - ダッシュボード内に埋め込む場合は、`sandbox="allow-forms allow-scripts"`（`allow-same-origin` を含めない）を設定した iframe を用い、親フレームへのアクセスを遮断する。
3. **VPN / Tailscale 直接接続への移行**
   - HTTP プロキシによる中継を廃止し、Tailscale Subnet Router や LAN 直接アクセス経由でのみルーター管理画面を開く運用とする。

## 2. ホストマシンの Cloudflare トークン権限（auth-db への書き込み）

### 現状とリスク
- **現状**: ホスト上のステータスサーバーが、メトリクス保存用の D1 トークンを用いて、共通認証基盤の `auth-db` に対して直接 SQL（認可コード消費やパスキー登録等）を実行する構成。
- **リスク**: 同一の Cloudflare アカウント内の D1 編集権限を持つ単一トークンをホスト上で保持しているため、ホストが侵害された場合に `auth-db` に対しても任意の SQL が実行され、他サービスを含むアカウント情報に影響が及ぶリスクがあります。

### 対策案
1. **Cloudflare Workers による内部 API ゲートウェイ化（推奨）**
   - ホストから `auth-db` への直接 SQL 発行を廃止し、共通認証基盤側に Service Token 等で保護された専用の内部 API エンドポイントを設ける。
   - 認可コードの消費やパスキー登録など、用途を限定した最小権限の API のみを提供し、直接の SQL 実行権限を剥奪する。
2. **Cloudflare アカウント / トークンのリソース制限**
   - 共通認証基盤（`auth-db`）とサービス基盤（ステータスボードのメトリクス等）で Cloudflare アカウントを分離するか、D1 データベース単位での権限分離を適用する。
3. **書き込み処理の認証基盤側への集約**
   - アカウントやパスキーに関する更新・管理操作を `auth` サービス側に一本化し、各サービスは読み取り専用に限定する。
